# Decisions (Roberto only, 16 Oct 2026)

Product name: **Thesaurus**, "un agente de pagos construido para Blinka" (Latin for tesorero). Never use Blinka's logo or present the product as Blinka's own; it is a hackathon prototype built for them.

## Stack
Cloudflare Workers (compute, deploy; native `ratelimit` binding, KV unused) + Supabase (Postgres with RLS, Auth with email OTP, Storage for invoice files) + AWS SES (all product email: OTP via Supabase custom SMTP, escalation mail; one IAM user scoped to `ses:SendEmail`/`ses:SendRawEmail` only, its SMTP credentials and access key live in Supabase auth config and `wrangler secret`, never in the repo; Roberto authorised this single IAM user on 16 Oct as the exception to the "no IAM users" rule) + Workers AI (reading only: PDF/image to text, schema-validated field extraction) + optional TypeSafe JEV behind a flag (see D3). UI: Vite + React served by the Worker (Static Assets). D1/R2 not used. Resend is NOT part of the product; the harness heartbeat keeps using it. Other AWS services are not used at runtime (a Worker cannot hold the 12h login credentials). SES region us-east-2.

SES facts that bind the build: the account starts in the SES sandbox (sends only to verified identities, 200/day). Task order: verify `HEARTBEAT_EMAIL` as an identity (Roberto clicks the AWS verification mail), create the IAM user + SMTP credentials, configure Supabase SMTP via the Management API, request production access (`aws sesv2 put-account-details`, AWS answers within 24h). Until production access is granted, OTP and escalation mail reach only verified addresses; the demo company direct access (D8) covers judges. `src/lib/email.ts` is the only sender; tests mock it; the README documents the one-file swap to another provider.

## Scope: in
- Ingest an invoice three ways, all through the same reader: upload PDF (text layer) or image; paste the text of an email; paste a chat message. Images go to the vision model; if reading fails the invoice enters as ESCALAR "ilegible". Reader failure never blocks ingestion.
- Reader: Workers AI turns the document into text and extracts payee, amount, currency, invoice number, issue date, due date, concept, each with a confidence; missing or doubtful fields are marked unknown, never guessed. Seeded invoices carry their extracted fields so the demo works even if the model is down.
- Beneficiary directory ("lo acordado"): name, country, currency, bank details (simulated), Blinka payment route (ACH, wire, SWIFT, Pix, CBU, COP transfer, USDC), agreement type (fixed retainer, hourly with cap, subscription, one-off) with amount, periodicity, validity.
- Policy: one active policy per company (MUST), edited in a form, never raw JSON; stored as a versioned JSONB document (name, version number, date). Rules: allowed beneficiaries (by bank account, not only name), per-payment limit, per-period limit and budget (USD), simulated USD account balance, human-approval threshold, duplicate window, agreement tolerance, due date, FX rate table (fixed per policy, printed in every record that used one). A rule left empty = "no se pudo verificar" = ESCALAR; an empty policy never pays. Saving a new version shows which pending/escalated invoices would change ("reevaluar pendientes" button); PAGAR and FRENAR decisions are final and never re-run. SHOULD: several policies with scope by beneficiary category (chosen from the directory, never by AI; ambiguity = strictest), JSON import/export.
- Decision engine: pure function `decide(invoice, beneficiary, policy, periodState) -> {outcome, checks[]}` with outcomes PAGAR / FRENAR / ESCALAR, run inside one SQL transaction with a per-company advisory lock so two simultaneous invoices cannot both pass the budget. Every check records name, actual value, threshold, verdict (cumple / no cumple / no se pudo verificar) and a template sentence in es and en. PAGAR only when every check is "cumple". Consequence table is fixed (D15). Period = calendar month, America/Bogota, by arrival date; budget and balance in USD; conversion `amount x rate` rounded to 2 decimals; currency without a rate = ESCALAR. Amount parsing handles `1.000,00` and `1,000.00`; total is cross-checked against line items and currency, mismatch = ESCALAR.
- JEV (SHOULD, behind `JEV_ENABLED`, off in the MUST path): two typed judgments only, "payee name is directory beneficiary Y" (Noul) and "possible duplicate of invoice X with a different number" (Noul). A judgment can only add an ESCALAR trigger; it can never produce PAGAR. Flag off or TypeSafe down = the deterministic rule decides (never UNKNOWN). Pitch line: the LLM reads, JEV doubts, the code decides.
- Decision record: a one-sentence headline; two columns, "Lo que leí" (extracted fields beside the document) and "Lo que decidí" (each check with the real value, the threshold and the arithmetic, e.g. "presupuesto octubre 50.000, usados 42.000, esta 9.000 -> excede"; "1.500.000 COP x 0,000245 = 367,50 USD"); "qué tendría que pasar para pagarla"; policy name + version + date; a timeline with actor and time (agente / Juan vía enlace / Juan en el tablero). Append-only: human approval/rejection is a new event; the agent's decision is never edited or deleted.
- Escalation: the approver (company field `approver_email`, may differ from the operator) gets an email (SES) with the invoice summary, what was read and the broken rule, and signed approve/reject links. The link opens a confirmation page; only the POST consumes the token (mail scanners open links). Approval overrides only the check that failed and re-runs the rest: if the budget is gone by then, it escalates again instead of paying. Approval consumes period budget; rejection releases it. Same actions in the dashboard.
- Screens (all with the guided intro of D19 and the language switch of D20): Bandeja (inbox with outcome and one-line reason, filters, "Ejecutar agente" over all pending with a n PAGAR / n FRENAR / n ESCALAR summary), Detalle de decisión, Política (form editor + "reevaluar pendientes"), Beneficiarios, Periodo (budget, balance, paid, committed, available, by beneficiary; autonomy % and violations computed against `expected_outcome`), `/demo` (public read-only view plus "Entrar como Andina Labs" direct access, D8) and the auth screens.
- Auth: signup and login with email + 6-digit OTP (Supabase Auth, template with `{{ .Token }}`, 10-minute expiry, custom SMTP = SES, configured by the Management API as an early task). Each signup creates its own company workspace seeded with the demo data set by a database trigger (no service role in the signup path), isolated by RLS on `company_id`. The service-role key lives in one module used by one handler (approval by token); everything else, CSV export included, runs with the user's JWT. Storage: private bucket, path `company_id/...`, RLS on `storage.objects`, 5-minute signed URLs. OTP verification rate-limited by Supabase; API routes rate-limited by the Workers `ratelimit` binding.
- Bilingual es/en, bounded: UI copy and record sentences in both from day one (template dictionaries, no i18n library); locale formats es-CO and en-US; language switch in the top bar. Emails and seed data are Spanish only.
- Output of a PAGAR decision: the record carries the payment fields in Blinka's shape (beneficiary, route, currency, amount). SHOULD: CSV export of the decision log for reconciliation.
- Data set: fictional company "Andina Labs Inc." (Delaware; team in Colombia, Mexico, Brazil, Argentina; vendors in LATAM, US, EU). 25-30 invoices in PDF, image, email text and chat text; USD, COP, MXN, BRL, ARS, EUR. ~15 normal and 10-12 traps: exact duplicate; duplicate with different number; new beneficiary; known beneficiary with changed bank account; over per-payment limit; over approval threshold but under limit; does not match the retainer; COP invoice whose USD equivalent exceeds the limit; exhausts the month's budget; exceeds the account balance; illegible / inconsistent total; past due; outside the period. Every seeded invoice carries `expected_outcome`; seeded fields are pre-extracted so the demo survives a model outage, but the decisions are always computed by the engine at seed time, never stored by hand.
- Tests: the decision engine has a test per trap case and per rule; the full suite runs in pre-commit. Playwright is used to record the happy path video on the deployed URL (a submission deliverable), not as a test gate; QA verifies by hand.
- Submission kit: `docs/SUBMISSION.md` with project name, jury description (<= 5000 chars, Spanish), demo URL and video URL (video file published at a URL the agents control).

## Scope: out (explicitly)
- Moving money, any payment API, Blinka integration, opening accounts, KYB/identity, compliance or fraud decisions, Blinka app design (challenge list).
- Multiple roles/permissions: one user per company is both operator and approver in the demo.
- Live FX rates from an external source (rate is a policy rule).
- AWS beyond SES at runtime (Textract, S3, DynamoDB): see Stack.
- Chat integrations (WhatsApp/Slack bots): chat ingestion is paste-only.
- Live inbound mailbox / Email Worker, `.eml` upload, AI-written summaries, live policy simulation (replaced by "reevaluar pendientes").
- Editing or deleting decisions. Reversing a FRENAR (the invoice is re-entered corrected).

## Product decisions
- D1: Three outcomes only: PAGAR, FRENAR (final, with reason), ESCALAR (waits for a human). Human answers are events appended to the record.
- D2: PAGAR is produced only by the pure decision function when every check is PASS. No prompt, model or JEV answer can write PAGAR. This is the disqualification guard.
- D3: Every rule is deterministic code. The LLM reads only. JEV is an optional layer behind `JEV_ENABLED` (off by default) limited to two judgments (name match, soft duplicate) that can only add an ESCALAR trigger; with the flag off or the service down, the deterministic rule decides.
- D4: Allowed beneficiary means name AND bank account on file. Same name with a different account escalates ("cuenta cambiada").
- D5: Period limit counts PAID + pending ESCALATED, evaluated in arrival order; the invoice that would exceed the budget escalates.
- D6: FX rates are a fixed table in the policy, printed in every record that used one.
- D7: Explanations come from templates filled with real values, in es and en, with the arithmetic shown. No AI-written summaries.
- D8: Every signup gets its own seeded workspace. `/demo` is a public read-only view of the demo company "Andina Labs" plus a direct-access button ("Entrar como Andina Labs") that opens a session on that company without OTP, with a "Reiniciar demo" button that re-seeds it (upsert-only), so a judge can create a trap invoice and change a rule without an account and without Roberto. The demo company never holds active approval tokens; its approver mail is HEARTBEAT_EMAIL. SHOULD: "Invitar" button that generates an access link without sending mail.
- D9: OTP and escalation mail go through SES as Supabase custom SMTP / from the Worker. While SES is in sandbox, mail reaches only verified addresses (HEARTBEAT_EMAIL first); the agents request production access as an early task. No MUST AC depends on production access: the demo path (D8) and the recorded happy path never need mail delivered to a judge.
- D10: Decision records and events are append-only, enforced by RLS (no UPDATE/DELETE policies on those tables).
- D11: Escalation links carry an HMAC-signed token (secret in `wrangler secret`), 48h expiry, stored only as a hash; single use is enforced by a unique index on the consuming event (insert ... on conflict do nothing), compatible with append-only. GET shows a confirmation page; POST consumes. The approval screen requires the token or a logged-in session of the same company.
- D12: No live inbound mailbox. Email content enters by paste.
- D13: Duplicate detection: exact (same beneficiary + same invoice number) is FRENAR. Soft duplicate (same beneficiary, same agreement concept and period, different number) is ESCALAR, without a percentage test, so a monthly retainer is never flagged against its previous month and a 2% surcharge does not slip through.
- D14: Spanish is the default language of the UI, the emails and the demo; English is a first-class switch for the UI and the record sentences.
- D15: Fixed consequence table, not configurable: exact duplicate and hard per-payment limit -> FRENAR; new beneficiary, changed bank account, approval threshold, period limit/budget, insufficient balance, agreement mismatch, past due, outside the period, illegible or inconsistent reading, missing rule, currency without rate -> ESCALAR.
- D16: PAGAR and FRENAR are final. A new policy version re-runs only pending and escalated invoices; the inbox states it.
- D17: Autonomy = share of seeded invoices decided without a human whose outcome equals `expected_outcome`; violations = PAGAR where `expected_outcome` is not PAGAR. Both are shown on the Periodo screen and asserted by the test suite.
- D19: Guided intro (MUST): after the first OTP login (and from a "Ver tutorial" link any time) a step-by-step tour walks the user through each part of the platform in the language they chose: a spotlight highlights the element being explained and the rest of the page is dimmed; one step per screen area (Bandeja, cómo entra una factura, Detalle de decisión, Política, Beneficiarios, Periodo, escalado y aprobación); Siguiente / Atrás / Saltar; "seen" is stored per user so it does not repeat. Built in-house (overlay + anchors, ~100 lines), no tour library.
- D20: Language choice es/en is offered on the login screen and in the top bar; the choice is stored per user and applies to UI, tour, record sentences and formats.
- D21: Design taste is a deliverable: every screen follows the preloaded `minimalist-ui` skill (editorial, warm monochrome, flat, no gradients, no AI-slop); the public `/demo` page and the login/landing use `design-taste-frontend`. The reviewer flags slop as a finding with the skill rule as the citation.
- D18: Policy applicability is never decided by AI: one active policy per company (MUST); with scoped policies (SHOULD) the scope comes from the beneficiary's category in the directory and ambiguity picks the strictest.

## Thesaurus is an agent (Roberto, 16 Oct 23:55Z, added after launch; product folds it into SPEC.md)
The challenge is "Agentes que pagan por la empresa" and Innovación (20%) is scored as "usa la IA con intención". Thesaurus must be, and visibly be, an AI agent, not a rules engine with a PDF reader. The safety rule does not move: the code is still the only thing that can write PAGAR (D2).
- D22 Agent loop, named as such everywhere (README, /demo, the tour, the record): **percibe** (the invoice arrives by any channel) → **lee** (the LLM turns the document into fields) → **consulta sus herramientas** (directory, policy, period, duplicates: deterministic tools the agent calls) → **decide** (the engine) → **actúa** (records, escalates, emails the approver with a concrete question, prepares the payment order) → **rinde cuentas** (the record). The code is organised the same way: `src/agent/` holds the loop and the tool calls; the engine is one of its tools.
- D23 The agent works alone (MUST): a Workers Cron Trigger every 5 minutes runs the agent over every company's pending invoices (scheduled handler, admin module), so an invoice pasted at 02:00 is decided at 02:05 with nobody logged in. The inbox says when the agent last ran.
- D24 "Lo que hice" (MUST): every record has, above the two columns, the agent's trace as numbered steps in plain language, generated from the actual run (not by an LLM): "1. Leí el PDF y encontré a Laura Méndez, 2.500 USD, factura #1042. 2. La encontré en el directorio: retainer mensual de 2.500 USD, cuenta terminada en 4821. 3. Verifiqué 13 reglas: 13 cumplen. 4. Decidí PAGAR. 5. Preparé la orden de pago: COP · transferencia."
- D25 The escalation is the agent asking a person a specific question, in Spanish, from a template filled with the failing checks: "Juan, la factura #2044 de Nube Sur LLC por 4.200 USD supera tu umbral de aprobación de 2.500 USD. ¿La pago?" with the two buttons. The same text appears in the dashboard's escalation card.
- D26 "Pregúntale a Thesaurus" (SHOULD S6, before S2): a chat box on the decision detail and on the inbox where a person asks in es/en ("¿por qué frenaste la factura 7?", "¿cuánto queda del presupuesto?") and the LLM answers grounded only in the record and the period state passed as context, read-only; it can never change a decision; answers are labeled "Respuesta generada por IA a partir del registro".
- D27 JEV stays as S2 (D3) and is pitched as the agent's "intuición rápida" layer; the pitch line in README and /demo: "El LLM lee, JEV duda, el código decide, el agente actúa."

- D28 Daily market FX (overrides D6 and the "Live FX rates" scope-out line). Rates change every day; the agent uses the market rate of the day. A Worker cron once a day (and on demand when today's row is missing) fetches USD pairs from Yahoo Finance's public chart endpoint `https://query1.finance.yahoo.com/v8/finance/chart/USD<CCY>=X?range=1d&interval=1d` (`meta.regularMarketPrice`, `meta.regularMarketTime`) for COP, MXN, BRL, ARS, EUR (+ any currency in the policy), with fallback `https://open.er-api.com/v6/latest/USD` when Yahoo fails. Google Finance has no API; Yahoo is the source shown to the user ("Yahoo Finance, 17 oct 2026 10:00"). Stored in an additive table `fx_rates(day, currency, usd_per_unit, source, fetched_at)` (upsert by day+currency). The source is pluggable: one module `src/lib/fx.ts` exposes `FxProvider { name; fetchRates(currencies): Promise<Rate[]> }` with the Yahoo provider as default and the fallback as second; the README and the Política screen say plainly that the company can connect another FX source (its bank, its treasury provider, Blinka's own rate) by adding one provider and setting `FX_PROVIDER`. The decision uses the latest stored rate; if it is older than 48 h or missing, the `moneda` check is "no se pudo verificar" = ESCALAR (never a guess). Every record prints amount × rate = USD, the source and the timestamp. The policy keeps an optional manual override table (finance can pin a rate); when present it wins and the record says "tasa fijada por la política". Seeded invoices stay deterministic in tests (fixture rates); the live demo uses market rates, and the expected outcomes of the seed must still hold with market rates (the builder checks the seed's margins and adjusts the seed amounts if a trap would flip).
